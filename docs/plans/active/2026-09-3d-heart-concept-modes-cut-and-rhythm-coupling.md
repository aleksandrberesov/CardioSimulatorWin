# Implementation Plan: 3D Heart dialog — concept rework (mode-driven rail, camera-relative cut, node/artery-driven real rhythms)

Source requirement: **`Docs/Concept/Симулятор ЭКГ 3D вид.pptx`** (customer, 2026-09-19; 3 slides, each annotating one mockup of the dialog).
Builds on **[2026-08-3d-heart-layers-coronary-perfusion-infarct-animation.md](../2026-08-3d-heart-layers-coronary-perfusion-infarct-animation.md)** (layers / coronaries / territories / package) and **[2026-08-eikonal-wavefront-solver.md](../2026-08-eikonal-wavefront-solver.md)** (wavefront, shipped).

> [!IMPORTANT]
> The single most important thing in this concept is **not** the layout. It is slide 3:
> *«Выбираем артерию – запускаем инфаркт – ритм тоже меняется. Причём ритм меняется динамически (сейчас этого нет, должен быть виден подъём сегмента ST)».*
> The dialog today is handed only a BPM (`MainScreen.xaml.cs:241` → `Heart3DDialog.ShowAsync(XamlRoot, bpm, isAdmin)`) and draws a **synthesised** PQRST template (`DrawEcgStrip`, `Heart3DDialog.cs:1050`). It structurally cannot show ST elevation. Closing that gap is the spine of this plan; the layout work hangs off it.

## 3. Architecture

### 3.1 Пресеты ритмов уже существуют — их не надо рисовать

«10 ритмов под типы проведения» и «10–15 ритмов под инфаркты» **не требуют авторинга волн**. Спина уже есть:

- `Taxonomy` (`Core/Domain/Taxonomy.cs:53`) — канонический словарь акронимов с полем `Group` (`sinus` / `conduction` / `infarction` / …).
- `Taxonomy.ResolvePathologyIdsForAcronyms(...)` (`:268`) — акронимы → id реальных патологий из пака.
- `MI_*` — 28 акронимов топической диагностики (`MI_ANT`, `MI_ANTSEP_STEMI`, `MI_INF_POST_OLD`, …), плюс `STE`/`STTU` (ОКС с подъёмом ST) и `STDD`/`STC` (без подъёма).
- Проводящие: `SR/ST/SB/SA/SAB/SARR` (СА), `AT/AF/AFIB/WAVN` (предсердия), `1AVB/2AVB1/2AVB2/3AVB/JEB/AJR/AVNRT` (АВ), `LBBB/RBBB/LAFB/LPFB/IDC` (His/ножки), `VER/AIVR/PVC/PVT/VFIB` (Пуркинье/желудочки), `WPW` (ДПП).

**Прецедент один в один** — панель «Лечение»: `TreatmentRhythmMap` (`Core/Domain/Treatment/TreatmentRhythmMap.cs`) держит `ClinicalRhythmState → acronyms[]`, хост берёт первый акроним, у которого есть настоящий ритм, и показывает его. Повторяем ровно это.

**[NEW] `src/CardioSimulator.Core/Domain/Heart3DRhythmMap.cs`** — чистый, data-only, юнит-тестируемый, портируемый на Android:

```csharp
public enum ConductionOrigin { SaNode, Atria, AvNode, His, BundleBranch, Purkinje, Accessory }

public static class Heart3DRhythmMap
{
    // Узел проведения → акронимы в порядке предпочтения (10 записей ≈ «штук 10»).
    public static IReadOnlyList<string> AcronymsFor(ConductionOrigin origin);

    // Коронарная ветвь (коды из CoronaryTaxonomy: LAD/LCX/RCA/…) → акронимы инфаркта
    // её зоны, STEMI впереди NSTEMI: LAD → MI_ANTSEP_STEMI, MI_ANTSEP, MI_ANT_STEMI, MI_ANT …
    public static IReadOnlyList<string> AcronymsFor(string vesselCode, bool stElevation);
}
```

`CoronaryTaxonomy` (vessel → territory → `affectedLeads[]`) — из M0 августовского плана; этот файл добавляет только слой «→ акроним».

### 3.2 Лента ЭКГ показывает настоящий ритм

`DrawEcgStrip` перестаёт быть единственным источником. Вводится `_stripSource`:

- **`Synthetic`** (по умолчанию, как сейчас) — шаблон `BuildEcgTiming(bpm)`. Нужен, потому что синхронизация ленты с проводящей волной завязана на тайминги узлов: R-пик садится на узел верхушки (см. `[[heart3d-ecg-strip-sync]]`). Режим «Анатомия» и свободный просмотр остаются на нём.
- **`Pathology(id)`** — сэмплы реальной патологии из пака. Выбор узла или артерии переключает сюда.

Сдвиг ленты (`ApplyEcgScroll`, `:1181`) — чистая функция от часов и ширины цикла, и остаётся ею: для реального ритма ширина цикла берётся из его RR, а якорь — из позиции R-пика (`SignificantPoints` / `EcgMeasurements`, ср. `[[pqrst-measurements-readout]]`), так что связь «R-пик ↔ верхушка» сохраняется и на настоящей волне.

**Почему это и есть ответ на «должен быть виден подъём ST»:** подъём ST не синтезируется — он приходит из реальной, размеченной врачом записи STEMI-ритма. Ничего не надо моделировать. (Генератор волн приложения *умеет* смещать ST — `Core/Domain/EcgElementGenerator.cs:16`, случай `StSegment` — но синтетический подъём поверх синтетического шаблона был бы клинически беднее реальной записи и его пришлось бы отдельно защищать перед заказчиком-кардиологом.)

### 3.3 Рейка режимов

```
[ Анатомия ] [ ЭКГ отведения ] [ Проводящая система ] [ Острый коронарный синдром ]
────────────────────────────────────────────────────────────────────────────────
  (секция выбранного режима)
```

`enum Heart3DMode { Anatomy, Leads, Conduction, Acs }` + `SetMode(...)`, которая (а) показывает одну секцию из четырёх, (б) применяет «вид по умолчанию» режима, (в) ведёт контекстную панель. Существующие группы **переезжают, а не переписываются**: `BuildConductionControls` (`:2384`) → секция Conduction, `BuildInfarctControls` (`:3856`) → секция Acs, `_leadsSchemeButton` (`:505`) → секция Leads. Кнопка `Monitor3DMi` (C2) исчезает — её роль забирает режим ОКС.

Виды по умолчанию на вход в режим: Анатомия — целое сердце, передний вид; ЭКГ отведения — схема отведений; Проводящая система — **разрез** (слайд 2) + просвечивание; ОКС — целое сердце.

`Просвечивание` и `Срез модели` дублируются кнопками в правом верхнем углу вьюпорта (`_viewportGrid`, `:542`) — место освободилось после снятия авторинга.

### 3.4 Срез со стороны зрителя (C3/C4)

- **Плоскость по камере.** `UpdateCutPlane` берёт нормаль из `camera.LookDirection`, а не из модельной оси Z; ползунок ведёт плоскость **от зрителя вглубь**, срезая ближнюю половину. Сердце можно вращать — рез остаётся «от нас». Пересчёт при отпускании орбиты (не каждый кадр: пересборка `Plane1` по всем `_cutNodes` — не покадровая операция).
- **Авторский разрез.** Эвристика `ComputeCutawayViewDirection` остаётся последним запасным вариантом, но перестаёт быть источником истины: направление вскрытия читается из манифеста (`cutawayView: [x,y,z]`, новое необязательное поле пакета из §12 asset-spec). Плюс ручной «перевернуть срез» на случай неудачной модели.
- **Качество разреза (референс со слайда 2) — это контент, а не код.** Рантайм-плоскость по полой оболочке даёт плоскую красную заглушку; камеры/клапаны/ход проводящей системы, как на фото, даёт только авторская геометрия разреза. Уходит в asset-spec как приёмочный критерий, не в код.

### 3.5 Контекстная панель (середина)

Плавающая карточка `BuildDescriptionOverlay` (`:665`) остаётся носителем, содержимое становится зависимым от режима: Анатомия — что видно и что можно сделать; Проводящая система — фаза цикла и что делает выбранный узел; ОКС — зона, поражённые отведения (`affectedLeads[]`), STEMI/NSTEMI, и **12-канальная миниатюра выбранного ритма** (это и есть «либо окно 12-канального ЭКГ»).

Для 12 каналов **не писать новый рендерер**: в приложении уже есть `Controls/EcgAssemblyControl.cs` (502 строки), сетка 12 отведений, сегодня используется экраном тестирования (`Screens/TestingScreen.cs`). Переиспользовать его.

## 4. Open questions (defaulted — confirm or override)

1. **Откуда диалог берёт ритм?** *Рекомендация:* `ShowAsync` принимает необязательный `PathologyEntry?` + доступ к списку патологий, ровно как панель «Лечение». Меняет ритм **только внутри диалога**; монитор под ним не трогаем, пока заказчик не попросит обратного.
2. **Меняет ли выбор артерии ритм на главном мониторе?** *Рекомендация:* **нет** в этом плане. Диалог — обучающий стенд; «протащить» выбор на монитор — отдельная, более рискованная работа (гейт TCP-хэндоффа, `[[monitor-freeze-tcp-handoff]]`).
3. **Что если в паке нет ритма под акроним?** *Рекомендация:* пресет в списке **скрывается**, а не показывает пустоту — как `TreatmentRhythmMap` решает про асистолию. Покрытие по `MI_*` проверить скриптом до реализации.
4. **Нужны ли именованные меши коронаров для выбора артерии?** *Рекомендация:* **нет, и это важно.** Селектор артерии — список, а не клик по 3D. Тогда весь ритмовый функционал (главная боль заказчика) **не заблокирован** поставкой модели от художника. Клик по ветви и подсветка приезжают позже, когда приедет `coro_<CODE>_*` (M3 августовского плана).
5. **Гейн ленты.** Мокап просит «10 мм/мВ», в коде 5 мм/мВ — половинный, чтобы зубец R помещался в 96 px. *Рекомендация:* дать ленте высоту под настоящие 10 мм/мВ (нижняя лента на макете заметно выше сегодняшней) и написать на плашке правду.

## 5. Milestones

Каждая веха самостоятельно проверяема в приложении.

### N1 — Срез со стороны зрителя  ✅ **сделано (2026-09-22)**

**Что оказалось на самом деле.** Шиппинговая модель (`Assets/Models/heart.glb`) содержит меш `heart_half`, поэтому `HasAuthoredCutaway == true` и «Разрезать» идёт **только** по ветке подмены кож. Ветка рантайм-плоскости на модели заказчика не выполняется вообще. Значит жалоба заказчика была именно про подмену кож — и она подтвердилась в живом приложении: до правки навигационный куб при нажатии «Разрезать» переключался с **F** (перед) на **R** (правый бок) — камера улетала вбок, и это читалось как «сердце развернулось, а рез пришёл из-за него».

Причина: `ComputeCutawayViewDirection` угадывала сторону вскрытия по разнице площадно-взвешенных центроидов двух кож. Предпосылка эвристики («материал убран с одной стороны ⇒ центроид смещён») для этой модели неверна — у вскрытой кожи площадь **больше** (0.0588 против 0.0503), потому что открылись внутренние стенки. Измеренное направление — `(0.83, 0.38, 0.40)`, то есть преимущественно **+X**, вбок.

**Правка:** камера на переключении разреза больше не двигается — зритель остаётся там, где был, и ближняя половина просто исчезает. Эвристика и её помощник `TryAreaWeightedCentroid` удалены (−91 строка).

**Проверено в приложении** (сборка Release, публикация, запуск, UIA+GDI): куб остаётся **F**, срез открыт к зрителю, видны камеры, септа и клапанный аппарат; повторное нажатие («Целое сердце») возвращает вид **попиксельно идентичный** исходному (diff = 0). 664 теста зелёные.

### N1.1 — Ветка рантайм-плоскости  ✅ **сделано (2026-09-22)**

Всплыло при N1 и было сначала откачено как «полупонятое». Разобрано по исходникам шейдера, который реально поставляется в HelixToolkit **3.1.2** (`vsMeshClipPlane.cso` из `HelixToolkit.SharpDX.dll`, сверено с исходником на коммите `0d10a9fc` и с дизассемблером `fxc /dumpbin`).

**Два правила, оба подтверждены байт-кодом:**

1. **Пространство — мировое.** Вершинный шейдер считает `output.wp = mul(input.p, mWorld)` и только потом отсекает по `wp.xyz`. Значит плоскость задаётся **в мировых координатах**, переводить её в локальную систему узла нельзя (именно на этом развалилась одна из ранних попыток: локальный масштаб 0.001 уносил плоскость за пределы модели). Отсечение — аппаратное, через `SV_ClipDistance`, отбрасывается строго отрицательное.
2. **`Plane1` читает `D` со знаком, противоположным `System.Numerics.Plane`.** `CrossSectionMeshNode.PlaneToVector` кладёт `p.D` в константный буфер как есть, а шейдер вычисляет `dot(N, wp - N*D)`. То есть поверхность лежит на `dot(N, X) = D` (через точку `+N*D`, а не `-N*D`), и остаётся половина `dot(N, X) >= D`. Привычный `new Plane(n, -dot(n, point))` даёт **ровно противоположную** половину. Нормаль обязана быть единичной — смещение масштабируется на `|N|^2`.

**Почему это не ловилось экспериментом.** Знаков два (нормаль и `D`), то есть четыре комбинации, и две «наполовину верные» дают правдоподобную картинку: концы ползунка выглядят правильно, а срезается не та половина. На этой модели обе половины с фронта читаются как красная масса, потому что меш `hear` — **только внешняя оболочка без внутренней анатомии** (ради этого художник и поставляет отдельный `heart_half`). Перебор знаков здесь сходиться не мог в принципе — нужен был исходник.

**Правка:** `normal = view` (единичный), `D = ` знаковая глубина плоскости вдоль оси взгляда, концы диапазона отодвинуты на `span * 1e-3`, чтобы `s = 0` не садился ровно на касательную к углу AABB. Плюс пересчёт среза на движение камеры в `OnCompositionRendering`.

**Проверено в приложении** на модели без `heart_half`, значения ползунка выставлялись через UIA `RangeValue` и считывались обратно (пиксельные клики по дорожке — причина недостоверности прошлых замеров). Разница с нетронутым кадром по ходу развёртки: `0 → 130839 → 177843 → 186855 → 188547`, то есть 0 — целое сердце, дальше передняя стенка вскрывается к зрителю, видны полость и срезанные в кольцо магистральные сосуды, 100 — пусто. Авторская ветка не затронута: срез даёт те же 133882 пикселя, что и до правки.

> [!NOTE]
> Практический предел этой ветки: раз плоскость всегда перпендикулярна взгляду, смотришь всегда прямо в срез, и увидишь ровно столько, сколько смоделировано внутри. У `hear` внутренностей нет — поэтому на шиппинговом контенте ветка и не нужна. Ещё из разбора: «крышка» среза (`CrossSectionColor`) рисуется полноэкранным квадом со стенсилом **на каждый** `CrossSectionMeshNode` и корректна только для замкнутых мешей; на оболочке она ненадёжна.

**Проверено в приложении** (Release, публикация, UIA+GDI): переключение всех четырёх режимов, в рейке видна ровно одна секция, активная кнопка выделена, Leads показывает торс со схемой отведений, Conduction открывается на половине сердца, возврат в Anatomy восстанавливает целое. 664 теста зелёные.

**Регрессия, найденная состязательным ревью диффа и починенная здесь же.** Вход в режим Conduction автоматически включает разрез, а разрез подменяет кожу — и волна деполяризации после этого красила ту кожу, которая только что ушла из вида. Цепочка: `PrecomputeWavefront` собирает только **видимые** меши, поэтому после загрузки `_activationTimes` ключи — внешняя кожа `hear`; `ToggleCutaway` меняет видимость на `heart_half`, но решение не пересчитывается; `ApplyWavefrontMaterials` идёт по `_activationTimes.Keys` и вешает материал на скрытые меши. Итог: «Волны деполяризации» в своём же режиме не делали ничего. Сам дефект был и раньше, но раньше разрез по умолчанию был выключен, и вход в диалог попадал в рабочее состояние — то есть новая рейка сделала поломанное состояние состоянием по умолчанию.

Починка: в ветке подмены кож `ToggleCutaway` возвращает уходящей коже её материал (`RestoreWavefrontMaterials`, вынесено из `ToggleWavefront`) и запускает `PrecomputeWavefront` заново — материал волны переназначается сам, когда решение приходит (`SolveAndApplyWavefrontAsync`). В ключ кэша решения добавлен флаг разреза: у двух кож разная геометрия, и без этого каждое переключение разреза выбрасывало чужую запись и платило за полный пересчёт.

**Проверено в приложении:** Conduction → Play → «Волны деполяризации» — волна идёт по **половине** сердца, заголовок фазы «QRS — His–Purkinje conduction», курсор на ленте синхронен; затем «Целое сердце» при работающей волне — волна переходит на внешнюю кожу. Межкадровая разница ~140–180 тыс. пикселей в обоих случаях (раньше в первом было бы 0).

## 6. Cross-cutting

- **Деградация обязательна.** Нет пака с зонами → селектор артерии всё равно работает (ритм + глобальный некроз). Нет ритма под акроним → пресет скрыт. Нет клипа `beat` → процедурная пульсация. Минимальная модель должна открываться и вращаться.
- **Ничего не синтезировать клинически.** Подъём ST, ритмы узлов, ритмы инфарктов — только из размеченного датасета через акронимы. Синтез допустим лишь там, где он уже узаконен (шаблон PQRST для режима без выбранного ритма).
- **Потоки.** Резолв патологий и сэмплирование волны — вне UI-потока, как `BuildAndApplyAsync`; пересчёт эйконала уже офф-тред и кэширован.
- **Тема** для новых оверлеев: `RequestedTheme = AppTheme.Current` (`[[dialog-webview-theme-propagation]]`); диалог — полноэкранный оверлей, так что light-dismiss (`[[dialog-light-dismiss]]`) касается только вложенных в него карточек.
- **Рендер-грабли:** Assimp тащит glTF как Phong, не PBR (`[[heart3d-infarct-texture-pipeline]]`); `PhongMaterial.VertexColorBlendingFactor` обязан быть 1 (`[[wavefront-vertex-color-rendering-broken]]`); материал импортированного сердца общий на несколько примитивов — кэшировать состояние по материалу, не по мешу (`[[heart3d-shared-material-caching]]`).
- **Проверка изменений UI — App Clicker** на Full-сборке (`CLAUDE.md`), `--paid` для N1 и N5 (нужен достоверный вердикт), `--free` для остального.

## 7. Risks

| Риск | Смягчение |
|---|---|
| В паке не окажется ритмов под часть `MI_*` или под какой-то узел | Тест покрытия в N3 **до** UI-работы; непокрытые пресеты просто не показываем |
| «Качество разреза» как на референсе рантайм-плоскостью не достигается | Явно вынесено в asset-spec как контентный критерий (§3.4); код делает только сторону и ракурс |
| Плоскость по камере при вращении = пересборка среза | Пересчёт по завершении жеста, не покадрово; при авторском разрезе плоскости нет вовсе |

| Мокап местами старше кода и тянет назад к уже снятому авторингу | Расхождения зафиксированы в §2; не регрессируем |
